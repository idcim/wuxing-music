## 后续发版顺序

1. 更新根 `package.json`、`package-lock.json`、`version.json`、`src/constants/version.ts`、`backend/app/version.py` 和 [路线图](../docs/ROADMAP.md)；安卓 `versionName` 从根 package 读取。
2. 在 [app/build.gradle](app/build.gradle) 增加 `versionCode`。当前是 `2000007`，后续新发布至少使用 `2000008`，还需对照后台已有版本，不能重复或降低。正式包名和签名不变。
3. 运行相关回归及构建。在本机已保存签名的账户执行 `npm run build:android:release`，后续更新不要再带 `-InitializeSigning`。
4. 构建脚本会验证正式包名、展示版本、非调试标记和既定签名，再输出 APK、`.apk.sha256`、`.apk.json`。核对原正式包的覆盖安装及受影响的功能。
5. 为新版本新增 `releases/<versionName>-<versionCode>.json`，以构建输出 JSON 为基础，补充准确的源码提交、更新内容、验证范围及本次交付动作。在本表增加历史行并更新当前交付；保留旧档案，不改写旧版哈希。
6. 后台「APP 管理」上传 APK 到 OSS，选择 `stable`，填写更新说明并保存草稿；检查平台解析出的包名、版本、大小和哈希。确认后按发布权限发布并开放下载，核对固定下载页及 APP 更新提示。仅推送 Git 不会完成此步骤。
7. 如需发布状态存档，新增日期明确的运营记录并注明依据；避免用旧本地 JSON 的状态冒充后台实时状态。错误发布应撤回并另发更高编号；原安装包、证书和对应源码提交一同保留。

`release-certificate.json` 是正式身份校验基准，普通发版不修改。若确需更换签名，先制定并验证签名轮换及旧用户升级方案，再调整相关登记；不要用更换指纹绕过构建校验。
