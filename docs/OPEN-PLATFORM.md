# 微信开放平台接入（用户互通）

> 目标：让同一个人在**小程序**与**公众号 H5**（以及将来的 **App**）登录时被认成同一个账号，
> 会员、订单、聆听历史、代理归因全部打通。
>
> 关键结论先说：**代码侧已经就绪，绑定本身不需要改一行代码**；
> 但**必须先把 v1.9.0 的合并逻辑上线，再去绑定**，顺序反了会伤到真实付费用户。

---

## 一、为什么必须"先上线、再绑定"

小程序与公众号是两个 appid，openid 互不相通。没绑开放平台之前，同一个人在两端登录会
**各建一条 `user` 行**。绑定之后微信开始下发 `unionid`，而两端的登录匹配顺序都是
`unionid > openid / oa_openid`：

```
绑定后，张三先打开 H5
  → unionid=U 查不到任何行 → 按 oa_openid 命中「公众号那条」→ 回填 unionid=U

张三再打开小程序
  → unionid=U 命中「公众号那条」→ 直接返回它
  → 而他买过年卡的「小程序那条」原地搁浅
  → 张三看到的是：我的会员没了
```

小程序是最早的用户盘（v1.0 就是纯小程序），**付费用户很可能正在那一侧**。
v1.9.0 的做法是在这一刻把两条行就地合并（见下），所以它必须先上线。

## 二、你要做的（运营侧，不需要 App 存在）

1. 注册**微信开放平台**账号 <https://open.weixin.qq.com>，主体与小程序/公众号一致。
2. 完成**开发者资质认证**（企业主体，¥300/年）。未认证拿不到 unionid。
3. 「管理中心 → 公众账号」把**现有小程序**和**现有公众号**都绑上去。
   - 绑定后两端的 `jscode2session` / `oauth2/access_token` 就会开始返回 `unionid`。
   - 小程序侧还需用户对小程序授权过（本项目 `wx.login` 静默即可拿到 unionid）。
4. 将来做 App 时，在同一个开放平台账号下创建「移动应用」，即可与前两端共用 unionid。

> 绑定小程序和公众号**不依赖 App**，所以这一步现在就能做完，与 App 排期无关。

> 绑完请到后台「设置中心 → 开放平台」把认证主体填上，并勾选已绑定的小程序 / 公众号。
> **绑定本身与那份配置里的 AppID/AppSecret 无关**——unionid 是微信自动下发的（见下一节）。
> 那两栏是**网站应用**的凭据，供浏览器扫码登录用，见下面第七节。

## 七、浏览器扫码登录（v1.11.0，可选）

微信外浏览器（Safari / Chrome）里的微信登录走的是**开放平台「网站应用」**，与 unionid
互通是两件独立的事：不做扫码登录也该绑定，做扫码登录则要在绑定之外多申请一个应用。

1. 开放平台「管理中心 → 网站应用 → 创建应用」，填网站名称、简介、图标与**网站 URL**。
   需要**审核**（一般 1-7 个工作日），且网站要可访问、已备案。
2. 审核通过后拿到该应用的 **AppID / AppSecret**，填到后台「设置中心 → 开放平台」。
3. 在该应用的「开发信息 → 授权回调域」里填 **H5 站点域名**（只填域名，不带 `https://`
   与路径）——就是公众号那边配的「网页授权域名」那一个，**不是管理后台的域名**。
   两边不一致，扫码后会报 redirect_uri 参数错误。
4. 未配置时后端回 `configured:false`，浏览器端不渲染扫码入口，不影响手机号登录。

> **扫码登录的账号怎么并**：网站应用的 openid 存 `user.web_openid`，与小程序、公众号的
> openid 互不相通，靠 unionid 串。绑定开放平台**之前**建的老账号，第一次扫码时认不出来，
> 会先另建一行；等这个人下次在小程序登录，`unionid` 命中新行、`openid` 命中老行，
> 就地合并（第四节那套逻辑，已验证会员保留在存活行上）。
>
> **浏览器里仍买不了会员**：微信支付在微信外浏览器要用 MWEB，尚未接。扫码登录后能听曲、
> 兑换 CDKEY、看历史与订单，点购买会失败。

## 三、代码侧现状（无需改动的部分）

两条登录路径本来就在读 unionid：

| 端 | 入口 | 取 unionid 的地方 |
| --- | --- | --- |
| 小程序 | `POST /api/mp/login` | `_jscode2session()` 返回的 `unionid` |
| H5（公众号） | `POST /api/mp/h5/login` | `_oauth2_access_token()` 返回的 `unionid` |

匹配顺序统一收在 `backend/app/user_merge.py::resolve_login`。

## 四、v1.9.0 加的东西

### 4.1 登录时自动合并（`user_merge.resolve_login`）

同一次微信授权会同时给出 `unionid` 与 `openid`。若前者命中 A 行、后者命中 B 行且
A ≠ B，就地合并 —— **这是唯一能把两条行认成同一个人的时机**，错过它另一条就永远搁浅。

- **保留哪条**：会员到期更晚的胜出；相同则保留 id 更小（注册更早）的。
- **搬什么**：`app_order` / `play_history` / `cdkey_redeem_log` / `commission` 的 `user_id`、
  `cdkey.used_by`、`agent.user_id` 全部改指向保留方；保留方缺失的字段
  （手机号、密码、生日、测评结果、代理归因、`oa_openid`、`unionid`…）从被并方补齐；
  会员取到期更晚的**一整组**（type/name/expire/source 同进同退，避免出现「年藏」配月卡到期日）。
- **不删行**：被并方留下并打上 `user.merged_into` 指针。历史订单仍指着它，删了无从追溯。
- **老 token 也安全**：`get_current_user` 会跟着 `merged_into` 走到存活行，
  否则用户拿旧 token 会落到一条搬空的行上，看着还是「会员没了」。
- **幂等**：`merged_into` 非空即跳过，反复登录只合并一次、只写一条审计。

### 4.2 审计（`user_merge_log` 表）

合并不可逆，必须留痕：保留方 / 被并方 / 触发原因（`unionid` 自动或 `manual` 人工）/
操作人 / 搬了哪些表各多少行 / 会员取了谁的。出争议时要能回答「他的会员是从哪条行来的」。

### 4.3 后台「重复账号」（用户页工具栏）

列出两类：

- **同 unionid 多行** —— 正常会在登录时自动合并掉，还留在这里说明有异常，优先看。
- **同手机号多行** —— **一律不自动合并**。家人共用号码是真实存在的，并错了不可逆，
  交给人工判断。绑定之前产生的孤儿账号主要靠这条找回。

人工合并需要 `users:merge` 权限（与「后台开通会员」分开授权）。
已合并的墓碑行不出现在用户列表里。

## 五、绑定后的验收

1. 找一个**在两端都登录过**的账号（最好是有会员的），先记下两条行的 id 与会员状态。
2. 在公众号 H5 里登录一次 → 后台看该行 `unionid` 是否已回填。
3. 再在小程序里登录一次 → 两条行应合并为一条，会员为两者中到期更晚的那个。
4. 后台「重复账号」里 **同 unionid 的分组应为空**。
5. `user_merge_log` 里能查到这次合并的明细。

## 六、遗留问题

- **绑定之前的孤儿账号认不回来**：两条行都没有 unionid，微信也不会追溯下发。
  只能靠手机号在后台人工合并 —— 所以**越早绑定，孤儿越少**。
- **小程序包不随自动部署**：登录逻辑在后端，所以合并对现有小程序包**同样生效**，
  这一条不用等传包。详见 [`WEAPP-TODO.md`](WEAPP-TODO.md)。
