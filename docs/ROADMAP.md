# 五行律音 · 版本路线图 (ROADMAP)

> 本文件（人读）记录各版本功能规划与状态；机读版本清单见根目录 [`version.json`](../version.json)（供未来 APP 更新接口读取）。发布时两者同步更新，并 bump `package.json` 与 `src/constants/version.ts`。

## 版本号规范（SemVer）

`主版本.次版本.修订号`：

- **主版本**：重大架构/不兼容变更（如小程序 → 多端 App）。
- **次版本**：新增功能（如 H5 端、离线能力）。
- **修订号**：修复与小改。
- `API_VERSION` 独立维护：后端接口契约不兼容时 +1，供灰度与兼容判断。

### v1.1.0 · H5 端（本次）

目标：H5 在**微信内**打开，登录与支付打通，与现有 openid 用户体系统一。

- **手机登录**：短信验证码 + 手机号密码两种（平台无关，小程序端亦可用）。

- **微信登录**：公众号网页授权（`snsapi_base`）换 openid，`unionid > openid` 并入现有用户。
  - 后端：`GET /api/mp/h5/oauth-url`、`POST /api/mp/h5/login`、`GET /api/mp/h5/jssdk-config`；配置 `oa_config`。
- **微信支付**：公众号 JSAPI，前端 `jweixin.chooseWXPay` 调起。
  - 后端：`create_jsapi_order` 支持公众号 appid；下单加 `channel` 参数。
- **落地哲学**：外部密钥（公众号/商户/短信）未配时走 dev/mock 兜底，无账号也能联调。
- 详细实施计划见团队计划文档（plans/）。

### v1.2.0 · H5 体验修复 + 大文件音频交付（本次）

**⚠️ 接口不兼容变更（API_VERSION 1.1.0 → 1.2.0）**
`POST /api/mp/bind-phone` 现在**强制校验 `scene=bind` 的短信验证码**（入参新增 `code`）。
此前任何登录态都能把任意号码占为己有，并因此白得一条「手机号 + 密码」登录路径。
**影响面**：线上小程序是手工上传的旧包，其绑定手机号请求不带 `code`，后端部署后会返回
400「请输入验证码」——需用开发者工具重新上传小程序包才恢复。H5 随服务器自动部署，不受影响。

**音频大文件（WAV 母版可达数百 MB）**
- 交付沿用 WAV 原文件，不转码。**流式播放靠浏览器/微信原生的 HTTP Range**：
  `<audio>` 与 `BackgroundAudioManager` 本就发 `Range: bytes=`，后端 `StaticFiles`
  自带 206，nginx 也未拦截——链路本就是通的，本次是把**看得见的部分**补齐。
- 不采用 `fetch + Range + MediaSource`：浏览器实测 `MediaSource.isTypeSupported('audio/wav')`
  为 **false**，MSE 不接受 WAV/PCM；手写 PCM 流式会丢原生 seek 与锁屏信息，且小程序端无法对等。
- 试听到点改为**释放音源**（清 `src`）而非仅暂停——暂停后底层仍会把整个文件缓冲完。
- 上传：分块落盘（不再整包进内存）、上限 `UPLOAD_MAX_MB`（默认 500）；
  大文件走 **OSS 直传**（`POST /api/admin/upload/oss-sign` 签 PostPolicy，锁定 object key 与体积）。
- nginx：`admin/nginx.conf` 补上缺失的 `/uploads/`（此前后台音频试听拿到的是 index.html）；
  两端 `/uploads/` 关 `proxy_buffering` 并升 HTTP/1.1。
- uvicorn 补 `--proxy-headers`，否则 `full_url` 在 HTTPS 后返回 `http://` 被当混合内容拦掉。

**新增依赖**：`qrcode[pil]`（H5 海报的普通链接二维码；小程序码只适用于小程序端）。

**上线后需人工确认**：OSS 桶配 CORS（否则海报 canvas 跨域污染无法生成）；
OSS/CDN 域名加进小程序 `downloadFile` 合法域名。

### v1.3.0 · 生日（农历 + 本命五行） + 后台登录验证码（本次）

**生日 → 农历 / 生肖 / 本命五行**

- 个人信息新增 **生日**（公历）与 **出生时辰**（可选），均用 `<Picker>`（全仓首次使用）。
  不走 `UserEditSheet`——Picker 内不含 `<Input>`，天然避开陷阱 14 那套「必须常驻挂载」的机制。
- **农历换算放后端**（`backend/app/lunar.py`，依赖 `lunar-python`）。前端不引库：
  小程序 16 页全在主包，农历库 200-300KB 会直接吃 2MB 额度；后端算一次三端口径必然一致。
  **实测小程序包 685KB → 689KB（+4KB）**。
- **生肖用春节口径**（`getYearShengXiao()`）而非立春口径（`ByLiChun`）：
  民间说「正月初二出生属鼠」用的是春节口径，立春口径是八字排年柱用的。
  两者在 1 月出生者身上会给出不同答案，代码里已注明，别当 bug 改掉。
- **`EightChar.setSect(2)` 显式写死**（库默认也是 2）。23:00 后出生的日柱归属命理上分两派，
  同一时刻 sect=1 得戊辰/土、sect=2 得丁卯/火。固定 sect=2 保证**本命五行始终跟用户填的公历日期一致**，
  不会出现「补填了时辰、本命五行就变了」。时辰真正的价值是凑齐四柱。
- **展示为并列关系**：「测评体质」（原「五行体质」）仍主导推荐曲目与配色；
  「本命五行」只做展示。文案保持趣味/文化口径，不做命理断言，不与健康疗效挂钩。
- 数据库两列 `user.birthday` / `user.birth_hour` 由 `_auto_migrate` 启动自动补，**无需迁移脚本**。
  存 0-23 钟点而非时辰序号，避开子时跨日歧义。

**后台登录验证码**

- 此前 `POST /api/admin/login` **既无验证码也无失败限流**，密码错了只回 400，可被无限撞库。
- 新增 `GET /api/admin/captcha`（免鉴权）：4 位字符，字符集去掉易混的 `0/O/1/I`（与 CDKEY 口径一致），
  TTL 5 分钟、**一次性消费**（验过即作废，无论对错）。
- 失败锁定口径直接对齐 `mp.py` 的手机号密码登录：同账号 10 分钟连错 5 次 / 同 IP 20 次 → 429。
- **不新增 Python 包**：Pillow 已随上版的 `qrcode[pil]` 进依赖；
  Pillow ≥10.1 的 `ImageFont.load_default(size=)` 返回可缩放字体，**镜像里不用塞字体文件**。
- 与 `ratelimit.py` 一样是**进程内存态**，多实例部署需换 Redis（源码已注明）。

**新增依赖**：`lunar-python`（106KB，无第三方依赖，与前端生态的 `lunar-javascript` 同作者同语义）。

**接口契约**：`/api/mp/*` 无不兼容变更（profile 仅新增可选字段），`API_VERSION` 维持 `1.2.0`。
`/api/admin/login` 新增必填的验证码参数属不兼容变更，但后台与后端同栈同时重建，不存在版本漂移窗口。
> 顺带修正：v1.2.0 只 bump 了 `version.json` 的 `api`，漏改 `src/constants/version.ts` 的 `API_VERSION`，本次补齐。

**小程序端**：本次改动同样需要重新上传小程序包才会生效，
且 `<Picker>` 的「确定 → onChange」这一步**只在 H5 验证过、未在小程序真机点过**。

### v1.4.0 · 代理分成（本次，默认关闭）

面向**实体店**（店内贴印刷推广码）与**网络推手**（分享海报）的成交分成。

**⚠️ 硬约束：只做一级分销。** 微信对小程序/公众号的多级分销（三级及以上）是封号级红线。
本设计只有「代理 → 用户」一层，数据模型上**刻意不留 `parent_agent_id`**——
留了口子日后必然有人接上去。

**开关贯穿三层，默认全关**（`agent_config.enabled=false`）：
- 接口：`/api/mp/agent/*` 与 `/api/admin/agents/*` 未开启一律 **404**（不是 403——
  403 等于对外承认「有这功能只是关着」）。例外是 `/settings/agent`，那是唯一的开启入口。
- 记账：`record_commission` 在未开启时**直接 return，不落库**。不是"记了不显示"——
  否则日后一开启会凭空冒出一批谁也解释不清的历史欠账。
- 界面：后台菜单按 `/me` 下发的 `features.agent` 过滤（`menu.ts` 的 `feature` 字段，
  路由守卫与 MainLayout 共用）；小程序/H5 的「代理中心」入口只在 `/agent/me` 返回
  `isAgent=true` 时渲染。

**归因：首次扫码永久绑定**（`user.agent_id` + `agent_bound_at` 两列，不建绑定表）
- 推广码走小程序码 `scene` / H5 链接 `?a=`，**复用早就通了的 `getQrcode(scene, page)`**
  （此前三处海报往 scene 里塞 `inv=<user.id>` 却全仓无人读取，是死负载）。
- 采集在 `app.tsx` 的 `useLaunch` 里先落本地 storage——**此刻多半还没登录**；
  真正的绑定挂在 `stores/user.ts` 的 `setUser`（五条登录路径的唯一汇合点，
  挂在每条路径上迟早漏一条）。
- 已绑定再扫别人的码**不改绑**且**不提示**——对用户不是错误，弹窗只是噪音。
- **拒绝代理绑自己**，否则等于全场自购返佣。

**分成产生与冲正**
- 挂在订单转 `paid` 的**两处**：支付回调与 `DEBUG` 下的 dev 直开分支。
- 与订单状态**同一次提交**，不会出现「付了款但没记账」的中间态。
- 幂等靠 `commission.order_id` 唯一约束（微信回调会重复投递），撞键用 SAVEPOINT 回滚。
- 金额与比例存**成交时点快照**，事后改比例不回溯历史，否则对账永远对不平。
- 礼物订单（`is_gift`）同样计入——买卡送人也是真实成交。
- 冻结期（默认 7 天）后转可提现。**不设定时任务解冻**：查余额时按
  `available_at <= now` 判定，少一个 cron 就少一处会悄悄停掉的组件。
- 退款冲正挂在 `confirm_refund`；已提走的钱追不回来，标 `clawback` 由人工追讨——
  冻结期的全部意义就是让这种情况尽量别发生。

**提现与打款**
- 金额一律以**服务端重算的余额**为准；同一代理同时只允许一笔在途；
  选记录用 `with_for_update()`（**MySQL 有效、SQLite 是空操作**，并发用例只能在 MySQL 上验）。
- 审核与打款分离：驳回 / 打款失败都会把金额**放回可提现池**（漏了这步余额会凭空消失）。
- **`payout_mode` 默认 `manual`**（线下转账 + 后台标记）。微信商家转账
  （`wxpay.transfer`，复用既有 v3 签名）是可切换项，切换前需：商户号单独开通
  「商家转账」权限、代理关联到微信登录过的用户、代理在微信里确认收款、
  大额需收款人实名加密串（**本期未实现**）。**本项目商户号尚未上线联调，该通路未经真实验证。**

**权限**：`agents:view` / `agents:manage` / `agents:settle`——钱的权限与管理权限分开授予。

**小程序端**：代理中心与推广码需重新上传小程序包才生效，见 [`WEAPP-TODO.md`](WEAPP-TODO.md)。

### v1.5.0 · 二级分成 + 下属视图 + 独立菜单

> ⚠️ **本节的分成算法已被 v1.6.0 整体推翻**，保留仅作历史记录。
> 当前规则见下面的 v1.6.0 一节，别照这里配比例。

**⚠️ 先更正 v1.4 的一处说法**：上一版把「不做二级分销」写成了硬约束，这比实际规则严。
红线是**计酬层级不得达到三级**（《禁止传销条例》的团队计酬、微信对多级分销的规定），
**二级是业界通行做法**。本次做二级，并把三级堵死——红线仍在，位置比原先划的靠后一格。

**分成算法：抽成从下级那份里扣，平台总支出不变**

```
base = 订单额 × 直推代理的一级比例   = 100 × 20% = ¥20   ← 平台支出，恒定
cut  = base   × 上级的二级抽成占比   = 20  × 25% = ¥5    ← 上级抽走
lvl1 = base − cut                    = 20 − 5    = ¥15   ← 直推实拿
```

- 无上级时 `lvl1 = base`，平台支出一模一样——上级那份不是额外掏的。
- **`lvl1` 由 `base − cut` 反算**，不能拿 `base×(1−rate2)` 独立取整，否则两条相加与 base
  差一分钱，对账永远对不平。已用 ¥0.99 / 33% / 50% 这类除不尽的组合验过零漂移。
- `rate2` 取**上级自己的** `commission_rate2`（None 则全局默认）——
  语义是「我作为上级能抽下级多少」，配在上级身上。
- **只走两跳，绝不递归**：琴行 → 小李 → 小王，小王的客户成交只付小王与小李，琴行 0。

**上下级：自动继承 + 永久**
用户被设为代理时，其 `user.agent_id`（当初扫码绑定的代理）即为上级。
落定后**不可改指向**，只允许为空时补填——允许改绑等于允许把别人的下级抢走，历史分成也讲不清。

**⚠️ 数据库：`commission` 的唯一索引必须换**
v1.4 是「一单一条」，`order_id` 建的是唯一索引；二级后一单落两条，旧索引会挡住第二条。
`_auto_migrate` 只加列不碰索引，故新增 `main.py::_fix_commission_index()`：
删掉 `order_id` 单列唯一 → 建 `(order_id, level)` 复合唯一 → 补回 `order_id` 普通索引。
幂等，失败只 warning。**已用「先建 v1.4 旧表结构再启动」的方式实测过迁移生效**。

**其它**
- `POST /api/admin/users/{id}/agent`：从用户页直接设为代理（此前只能手填 user_id）
- `GET /api/admin/agents/{id}/downline`、`GET /api/mp/agent/downline`：下属视图（只看一层）
- 后台新增独立的「代理分成」子菜单，**逐项**门禁：前三项要模块已开启，
  「分成设置」常驻——关闭时菜单里只剩它，既没摊开功能又不会让人找不到开关
  （v1.4 把开关埋在设置中心的 tab 里，实际用起来找不到）。
- `void_commission` 由 `.first()` 改 `.all()`：退款必须把直推与上级两条**都**冲正，
  否则上级的抽成留在账上照样能提走。

### v1.5.1 · 推广海报重做

**先是个 bug，不只是不好看。** H5 上海报的**所有文字都渲染成 24px**——
`Taro.createCanvasContext`（已弃用的旧画布 API）在 H5 shim 里，
`setFontSize`/`setTextAlign` 是**立即**写 `ctx` 的，`fillText` 却是**入队**等 `ctx.draw()` 回放的：

```js
set font(e) { this.ctx.font = e }                    // 立即
fillText(...a) { return this.enqueueActions(...) }   // 入队
```

于是回放时字体停在最后一次设的值（底部提示的 24px），「木」（设计 140px）、
主标题（48px）全被压成 24px。小程序端走原生实现，不受影响。

**改用 Canvas 2D**（`<Canvas type="2d">`）——立即模式，没有队列，这个错位从根上消失；
且两端都是标准 `CanvasRenderingContext2D`，绘制代码真正共用。新目录 `src/services/poster/`

### v1.6.0 · 分成改加法模型（本次）

**为什么改**：v1.5 的减法模型让代理**拿不准自己能拿多少**。同样谈好 20%，
被招募进来的代理实际只拿 15%，还取决于上级配了多高的抽成——他自己控制不了。
对下级不公平，招人时也不好说。

**新规则：直推恒定拿满，上级加成由平台额外支出**

```
direct = 订单额 × 直推的一级比例   = 100 × 20% = ¥20   ← 恒定，与有没有上级无关
bonus  = 订单额 × 上级的加成比例   = 100 ×  5% = ¥5    ← 平台额外支出
平台总支出 = ¥25；直推若没有上级，则这一单只出 ¥20
```

- **平台总支出改为浮动**（20% 或 25%）。上级那 5% 是净增成本，等于给发展下线的人发奖励。
- 两条**各按订单额独立取整**，不再有「两条相加等于 base」的跨行不变量，
  也就不需要 `base − cut` 反算了。对账按单汇总 `amount`；
  合计与 `订单额×(r1+r2)` 可能差 ±0.01（¥33.33 → 6.67+1.67=8.34），可接受。
- `rate2` 仍取**上级自己的** `commission_rate2`，但**语义反过来了**：
  从「我能抽下级多少」变成「我发展的下级，每单我额外多拿订单额的多少」。
- **只走两跳，绝不递归**不变：琴行 → 小李 → 小王，小王的客户成交只付小王与小李。
- 顺带修掉一个反向激励：旧模型里**停用上级会让直推多拿钱**（`base − 0`）；
  新模型下上级停用与否，直推都拿满自己的比例。

**⚠️ 全局配置键必须改名，不是可选项**
`agent_cfg` 是 `{**DEFAULTS, **saved}`。只要有人打开过后台「分成设置」点过保存
（**哪怕开关是关的**——`settings.py` 无条件写入完整 `model_dump()`），库里就存着
`default_rate2: 0.25`。若沿用旧键名，这个 0.25 会被新语义读成「订单额的 25%」，
上级分成从 ¥5 变 ¥25，平台每单支出 45%。
故改名为 **`default_bonus_rate`**（默认 `0.05`），合并时旧键自动失效，零迁移代码。
> 单个代理的 `commission_rate2` 覆盖值救不了（改 DB 列不值当）。上线前查一次：
> `SELECT id, name, commission_rate2 FROM agent WHERE commission_rate2 IS NOT NULL;`
> 有结果就手工置 NULL。

**⚠️ 最大赔付从 100% 变成 200%**
旧模型总支出恒为 `订单额 × rate1`，被 `rate1 ≤ 1` 结构性兜住。加法模型下支出是
`订单额 × (rate1 + rate2)`，而这两个数**分属两个不同的 Agent 行**，各自只校验 `≤1`。
三道防线：① `AgentSettingIn` 的 `model_validator` 拒绝全局 `rate + bonus > 1`；
② `record_commission` **运行时钳制**（唯一硬保证，超了削**上级加成**而非直推——
直推那个数是印在海报上谈好的）；③ 后台演算块把总支出显式算出来并在超标时变红。

**出参与文案**
- `/api/mp/agent/me` 删掉 `upline` 块（代理拿满自己的比例，没有"被抽走"可解释）；
  `/api/mp/agent/commissions` 不再下发 `baseAmount`（那是平台成本，代理不该看到）。
- `/api/admin/commissions` 的 `baseAmount` → **`platformCost`**（本单平台总支出），
  并新增 **`parentName`**——后台在 level=1 的行上也要能看出这代理归谁。
  顺带把该端点的 `db.query(Agent).all()`（水化全部实体）换成三列查询，比原来更省。
- 全线「抽成」改「加成」；后台代理列表加**直属代理 / 下级代理**标识
  （刻意不叫「一级/二级」——会与分成记录的 `level 1/2` 撞车，那是两回事）。

**验证**：仓库无测试框架，用一次性脚本内存 SQLite 直接驱动 `record_commission` /
`void_commission` 跑了 12 组：无上级 / 有上级恰好 20+5 / **直推 0% 但上级有加成
（旧代码 `if base <= 0` 会把上级那条一起吞掉）** / 全零 / 超 100% 钳制 / ¥33.33 取整 /
退款两条都冲正 / 幂等 / 冻结与解冻 / 上级停用 / **存量旧键 0.25 不再生效** / 模块关闭不落库。

### v1.8.1 · 三个实测缺陷（本次）

v1.8.0 上线后实测发现的三处问题，都不是这次改动引入的，是一直存在、这回才被摸到。

**一、播放进度轴拉不动 —— Taro `<Slider>` 在 H5 上基本不能用**

读 `node_modules/@tarojs/components/dist/collection/components/slider/slider.js` 就一目了然：

1. `componentDidLoad` 只把 `touchstart/touchmove/touchend` 绑在 **`this.handler`**，
   也就是 `.weui-slider__handler` 那个圆点上 —— **轨道上点按拖动一概无效**，
   必须精准摁住圆点；而我们传的 `blockSize={16}`，命中区只有 16px。
2. **完全没有 mouse / pointer 监听** → 桌面浏览器里 100% 拖不动。
3. `value` 上挂着 watcher，属性一变就 `updateByStep()` 重置内部 `percent`；
   而 `onTimeUpdate` 每秒推好几次 `currentTime`，**拖到一半会被播放进度拽回去**。

改为自绘 `src/components/SeekBar`：整条 88rpx 高的命中区可点可拖（不用 `::before` 撑——
伪元素在小程序端不参与父节点触摸命中）、拖动期间以手指位置渲染并忽略 `currentTime`、
松手才 `seek`、H5 另经 `document` 补一套鼠标拖动（Taro 的组件 props 只声明了 touch 系列）。
缓冲轨道并进同一条，顺手去掉了以前用负 margin 把缓冲条叠在 Slider 上的写法。

> 排查记录：一度以为是 `taro-slider-core` 没水合（线上实测 `hydrated: false`、宽度 0）。
> 但做对照实验发现**同环境下 `taro-view-core` / `taro-text-core` 也全是 `hydrated: false`**，
> 而页面明明正常显示 —— 说明那是自动化浏览器的测量假象，不能拿来判断真机。
> 这正是 `CLAUDE.md` 已记的那条坑（输入框相关行为本地复现不了）。最终结论来自读源码，与环境无关。

**二、会员专属曲目无法试听**

`player.ts::onTimeUpdate` 里 30 秒断流 + `UpgradePrompt`（「试听结束 / 开通会员」）
早就写好了，但**永远走不到**：首页 / 探律 / 元素详情三处都是
`onPlay={() => (locked ? goMember() : onTrack(t.id))}` —— 非会员点付费曲目直接跳会员页，
从来没机会开始播。于是「把曲目设为会员专属」的实际效果是彻底锁死而不是试听 30 秒，
与 `CLAUDE.md`、套餐文案（「30秒曲目预览」）和 `UpgradePrompt` 的措辞全都对不上。

改为一律 `onPlay={() => onTrack(t.id)}`，由 store 的 `previewSec` 断流兜底。
曲目卡也不再对会员专属曲目画锁头（画锁头会让人以为点不动），换成「试听 30s」徽标。

**三、H5 输入框文字贴顶**

Taro 把 `className` 落在外层 `taro-input-core` 上，它是 `display: block`；
而内层真正的 `<input class="weui-input">` 被 Taro 自带样式把高度钉死在 `1.47059em`（约 23px）。
于是我们设的 96rpx 高度只撑开了盒子，真 input 作为块级子元素贴在顶部，下方空一大截。
登录 / 兑换码 / 资料编辑 / 个人信息四处全中招。
在 `app.scss` 加一条全局 `taro-input-core { display: flex; align-items: center }` —— 
小程序端没有这个标签，规则不命中，无副作用。

### v1.8.2 · 试听断流后播放键永久转圈（本次）

**症状**：试听结束提示弹过一次之后，回到播放详情页点大播放键，一直转圈、不出声、
点了没反应，只能刷新页面。

**这是 v1.8.1 暴露出来的存量缺陷**，不是它引入的：v1.8.1 之前没有任何入口能触发
试听断流（付费曲目点了直接跳会员页），所以「断流之后再播」这条路在生产环境从未跑过。

**根因一：看门狗只写文案，没解除 `isLoading`**

```js
loadTimer = setTimeout(() => {
  if (get().isLoading && !get().isPlaying) {
    set({ loadError: '加载较慢，请检查网络后重试' });   // ← isLoading 仍是 true
  }
}, 15000)
```

而播放器页的 `toggle()` 第一行是 `if (isLoading) return`。于是只要一次加载没能等到
`canplay`，播放键就**永久失效**且一直转圈——这正是用户描述的现象，也解释了「只能刷新」
（刷新即重置内存态）。现在超时同时置 `isLoading: false`。

**根因二：`release()` 拆掉音源却没摘回调**

`removeAttribute('src') + load()` 之后元素仍会吐 `abort` / `emptied` / `stalled` / `waiting`，
其中 `stalled` 与 `waiting` 都接在 `onWaiting` 上 → `set({ isLoading: true })`。
此刻已经没有音源，`canplay` 永远不会来把它清掉。现在 `release()` 先 `bound = {}` 再拆，
`load()` 时自然会重新赋值。小程序端 `BackgroundAudioManager.stop()` 后同样可能回调
`onWaiting`，一并修。

**另**：播放器主播放键在 `loadError` 时兼作重试（与 MiniPlayer 一致），
此前出错后主按钮是个死键，只有下面那个小重试按钮能用。

**验证的边界（要如实说）**：桌面 Chrome 上这条路径本来就是通的——
断流后点播放能正常从 0 重播，`canplay` 总是立刻到达，**这个卡死复现不出来**；
往元素上补发合成 `waiting` 也没能让它卡住。所以本次修的是**读代码可证的结构性缺陷**
（看门狗那条尤其确定），而不是一个已复现的失败用例。需要在真机上回归确认。
